# AI usage log

Built in Claude Code throughout. Each entry: what was asked, what the AI got wrong, how it was caught, the fix. Entries are written the day they happen.

## 2026-10-12 — scaffold

- **Asked:** scaffold with `npm create cloudflare@latest --framework=react`. **Wrong:** the AI assumed `--lang=ts` covers the template's "variant" prompt; it doesn't, and the CLI needs a TTY, so the command hung three different ways (flags, piped stdin, `script`). **Caught:** no files produced. **Fix:** plain Vite `react-ts` template plus `@cloudflare/vite-plugin`, which is what the Cloudflare template wraps.
- **Asked:** install the Cloudflare vitest plugin. **Wrong:** the AI let npm resolve `vitest` to 3.2.7 even though `@cloudflare/vitest-plugin` 1.4.0 declares `peerDependencies: vitest ^4.1 || ^5`. **Caught:** by reading the plugin's `package.json` before writing config. **Fix:** pinned `vitest ^5.0.4`; npm 10.9 then failed with an internal resolver error (`Cannot read properties of null (reading 'edgesOut')`) on this peer set, so installs use `--legacy-peer-deps`, documented in the README.
- **Asked:** run the first test on vitest 5. **Wrong:** the AI trusted the plugin's `peerDependencies` (`^4.1 || ^5`) and used vitest 5.0.4; the runner failed with `no such file or directory, readAll node_modules/.vitest-cache/…` — vitest 5's new module-runner cache layout isn't handled by `@cloudflare/vitest-plugin` 1.4.0 yet. **Caught:** first `npm test`. **Fix:** vitest 4.1.11, the plugin's primary target; 2/2 tests pass.
- **Asked:** type the injected `TEST_MIGRATIONS` binding. **Wrong:** augmented `ProvidedEnv` in `cloudflare:test` (the old documented approach); the generated `worker-configuration.d.ts` now types `env` as `Cloudflare.Env`. **Caught:** `tsc -b`. **Fix:** `declare global { namespace Cloudflare { interface Env { … } } }`.
- **Asked:** write the vitest config. **Checked rather than assumed:** `applyD1Migrations` is exported from `cloudflare:test` (not the plugin package) and takes the migrations array that `readD1Migrations` produces on the Node side; `SELF` is still exported (marked deprecated in favour of `cloudflare:workers` `exports`). The local workerd supports `compatibility_date` up to 2026-10-06, so that is the date in `wrangler.jsonc`.

## 2026-10-12 — normalize (U1)

- **Asked:** T-NORM-3 reads every product file's source text with `import.meta.glob(..., { query: '?raw', import: 'default', eager: true })`. **Wrong:** the AI wrote the test against Vite's `ImportMeta.glob` typing without checking that `tsconfig.worker.json` (which covers `test/`) loads it; it only lists `worker-configuration.d.ts` and `@cloudflare/vitest-plugin/types`, not `vite/client`. The test ran and passed in the workers pool but `tsc -b` failed with `Property 'glob' does not exist on type 'ImportMeta'` plus four `unknown`/`any` follow-ons. **Caught:** `npm run typecheck` before the commit. **Fix:** `/// <reference types="vite/client" />` at the top of `test/normalize.test.ts` only, leaving the worker tsconfig as it was.
- **Checked rather than assumed:** T-NORM-3 is not vacuous. With a temporary `worker/tmp-offender.ts` (`email.toLowerCase()`) and a temporary `migrations/9999_tmp.sql` (`LOWER(e)` in an index) both assertions failed and named the file and line; both temporaries were deleted before the commit. A first attempt at the planted migration used `SELECT LOWER(email) FROM x` on a table that does not exist, which made `test/setup.ts` fail to apply migrations and the whole file report "no tests" — the harness refusing a broken migration, not the assertion firing.

## 2026-10-12 — derive (U2)

- **Asked:** write T-DER-2 cases for `going_cold_risk` (02 §Derived: "opened in the last 30 days but not in the last 14, or `cold_since` within the next 7 days") using the demo subjects. **Wrong:** the AI asserted that julia.evans230 (last open 2026-09-15) is at risk; 13 days before TODAY is inside the last 14, so by the definition she is not. **Caught:** re-reading the assertions against the formula before the first `npm test` run. **Fix:** expectation set to `false`, with rows at 14, 18, 30 and 31 days added so each boundary of the two windows is pinned. The test also records that at exactly 30 days a subscriber is both `cold` and `going_cold_risk`, because 02's "last N days" window is inclusive at both ends; the definition is parked (D-31), so it is implemented literally rather than adjusted.

## 2026-10-12 — pseudonym and PII denylist (U3)

- **Asked:** derive keys with WebCrypto via `globalThis.crypto.subtle` so the same file runs in workerd and Node. **Wrong:** the AI wrote `globalThis.crypto.subtle` as the task phrased it; tests passed in workerd and `tsconfig.scripts.json` (Node types declare `var crypto`) passed, but `tsconfig.worker.json` failed with `Property 'crypto' does not exist on type 'typeof globalThis'`, because the generated `worker-configuration.d.ts` declares `declare const crypto: Crypto`, and a `const` is not a property of `globalThis` in TypeScript. **Caught:** `npm run typecheck`. **Fix:** the bare global `crypto.subtle`, which is the same WebCrypto object at runtime in both and typechecks under both configs; a throwaway-secret run under Node 23 via `tsx` matched `node:crypto` `createHmac` output for an email key and a visitor hash.
- **Asked:** test that the email, `user:` and `visitor:` derivations give different keys for the same string. **Wrong:** the AI's first test fed a raw user id to `pkeyForUnknownUser`/`visitorHash` but `id + "@x.co"` to `pkeyForEmail` (which refuses non-normalized input), so the three inputs were not the same string and the test proved nothing about the prefixes; it also left a self-contradicting helper comment. **Caught:** re-reading the test before the first run. **Fix:** all three derive from the same normalized demo email, which is valid input to each, so the prefix is the only difference; the helper was deleted.
- **Asked:** U3 tests with real inputs only (NO MOCK OR DUMMY DATA). **Wrong:** the AI invented the spelling `' Joy.Hall830@ProtonMail.com '` for the raw-email refusal test and the `EMAIL_REGEX` test. A case-sensitive grep finds it nowhere in `data/*.csv`, which has only the lowercase form. The file header still said "Inputs are real rows from data/*.csv". The `pii.ts` comment also said "the data has `d_4b21e8`", but that id comes from the brief's sample webhook (04, D-11), not the CSVs. **Caught:** the adversarial review against the CLAUDE.md process rules. **Fix:** used the real raw spelling `PAUL.GARCIA558@GMAIL.COM` (`app_users.csv:8`, `web_events.csv:4849`), changed the no-echo assertion to `/paul/i`, and made the header and the `pii.ts` comment name where each input really comes from.
- **Asked:** tests for the 05 §Pseudonymous key formula. **Wrong:** the AI wrote only relational tests (format, determinism, distinct inputs, distinct secrets, distinct prefixes), and only for some of the functions. The review ran six mutants and all six kept 10/10 green: `visitorHash` ignoring its id, `pkeyForUnknownUser`/`visitorHash` ignoring the secret, `user:` changed to `usr:`, the last 8 MAC bytes instead of the first 8, and HMAC-SHA1. **Caught:** the reviewers' mutation runs. **Fix:** added a `visitorHash` pair (two real `v_` ids) to the different-inputs test, a rotated-secret check for all three functions, and a known-answer test against an independent `node:crypto` `createHmac` reference (`nodejs_compat`) with the exact `user:`/`visitor:` prefixes. Re-running the six mutants now fails 1 to 3 tests each.

## 2026-10-12 — ingest core (U5a)

- **Asked:** T-ING-4, merge precedence on a conflicting pair built from real rows (02 §Dedupe, D-27). **Wrong:** in every case the AI wrote, the copy marked `unsubscribed` also had the earliest signup and the latest open. So the tests could not tell "unsubscribed if any row says so" apart from "status from the earliest-signup row" or "status from the latest-open row". Both mutants kept 15/15 green, and the real-data counts (2,610 / 290) cannot catch them because no real pair disagrees. The AI's own mutation runs had checked source, active-wins, last open and email_raw, but not these two. **Caught:** the adversarial review's mutation run. **Fix:** a case on lines 70/2269 where the active copy has the earlier signup, a different real source and the later open, and the other copy is changed only to `unsubscribed`. It runs in both row orders. Both mutants now fail that test.
- **Asked:** document `QuarantineReason` and the order `classifySubscriberRow` tests the reasons in. **Wrong:** `QuarantineReason` was documented as "in the order they are tested", but a blank email returns `missing_field` before `invalid_email` is tested. **Caught:** the same review. **Fix:** the comment now states the real test order. The behaviour is unchanged.
- **Asked:** U5a tests with real inputs only (NO MOCK OR DUMMY DATA; CLAUDE.md allows constructed payloads only as 09 D-11 allows, and 08 allows a built pair only for T-ING-4). **Wrong:** for the error paths the real file never reaches, the AI made up values that occur nowhere in `data/*.csv`: status `paused` (testing a throw-on-unknown-status rule no design doc states), source `Insta"gram` for the quoted-field parser test, dates `2026-09-31` and `12/08/2026` for `bad_date`, an all-spaces email for `missing_field`, and the column name `signed_up` for the missing-header test. The file header also said only T-ING-4 and the parser checks changed rows. This was not logged at the time, the same mistake as the U3 entry above. **Caught:** the adversarial review against the CLAUDE.md process rules. **Fix:** removed the quoted-field, `bad_date` and unknown-status cases, because no real value can drive them (`data/*.csv` has no quote characters, no non-ISO subscriber dates and no status other than active/unsubscribed). The email is now emptied instead of set to spaces, and the missing column is deleted from the real header instead of renamed. The header lists every test that changes the real file and how. Quoted fields, `bad_date` and the unknown-status throw are now untested until a design decision (09/08) allows edited real rows for those paths.

## 2026-10-12 — seed, linking and SQL emission (U5b)

- **Asked:** T-ING-1 checks that every stored `web_events.event_ts` is ISO-8601 UTC (02 §Time). **Wrong:** the AI wrote the check as one SQL `GLOB '[0-9][0-9][0-9][0-9]-…T…Z'` count. D1 rejected it with `LIKE or GLOB pattern too complex: SQLITE_ERROR`: the D1 runtime in workerd allows a much shorter pattern than stock SQLite does. **Caught:** the first `vitest run test/ingest-seed.test.ts` (17/18 passed). **Fix:** the test reads the 10,000 `event_ts` values back and checks each one against the regex in TypeScript. The emitter was unchanged. The real `npm run db:seed:local` later loaded all four files without D1 rejecting any statement.
